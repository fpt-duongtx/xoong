# Where xoong's bytes and time go

The screens are the plain ones a user writes; nothing is tuned. One run per instrument (each on a fresh page): read the percentages, not the last digit.

Ranked by (share of the measured time or bytes) x (ease), from the tables above. "Share" is of the 10,000-row creation (639 ms) unless said otherwise.

| # | Opportunity | Evidence | Share | Ease |
|---|---|---|---|---|
| 1 | **Never-executed JS shipped on every page**: `router.js`, dialogs, form generator, column picker, array forms, `mutate` and the rest of the graph are fetched and parsed though the screen runs none of them | 49% of the 245 KB of JS loaded never runs on the people screen (45 to 61% of every package); 63% on the nested page; `router.js` alone is 21 KB | bytes: about 120 KB raw (a third of the gzip); load: the graph is ready at 875 ms on slow 4G, of which 33 requests and parse | medium: lazy `import()` of router, dialogs and the schema form, behind the elements that need them |
| 2 | **Allocation per row**: 7.4 KB per row; `bindNode` allocates 3.3 KB (44%) per row, native `Set`/`Map` another 1.1 KB (a `Set` for the deps of each effect and the subscribers of each signal), `denormalize` 0.4 KB, `makeRow` 0.3 KB | 72 MB allocated for 10,000 rows; GC background marking 167 ms against Angular's 104, main-thread GC 54 ms against 39 | GC about 25% of the creation time | medium: sets created lazily (most signals have one subscriber), no per-node arrays (`getAttributeNames`, `[...childNodes]`), no per-row closures where a plain read is enough |
| 3 | **Style recalculation**: 101 ms against 64 ms for the same table drawn by plain CSS | `UpdateLayoutTree` in the trace; the table rules of `xoong.css` (descendant selectors with `:where`, `tbody tr:last-child td`, a `transition` on `tbody`, `[data-refreshing]` opacity) | about 6% of the time (37 ms over the plain table) | easy, but measured afterwards: with no stylesheet style recalculation is still 86 to 95 ms, so the CSS is not the cause (see CHANGES.md) |
