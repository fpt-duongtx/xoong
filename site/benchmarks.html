Benchmarks

Measured, not promised. The same people screen built in xoong, in a React stack and in a Vue stack, run in real Chromium; plus the speed of the xoong command and of xoong-mcp. Every number below is generated from JSON files in the repository by scripts you can run, and the page is rebuilt from that data, so the two cannot drift apart.

Read this first. These are the results of one machine (Apple M1, 8 cores, 8 GB RAM, Darwin 25.2.0 (arm64), Chromium 158.0.8127.18, Node 24.7.0, 2026-11-09) with 5 runs per number after one warm-up run: the median is shown with the smallest and largest run in brackets. Numbers depend on the machine, so use them to compare the columns of one table, not to predict your users' devices. One screen, one team of one author: this is an honest comparison of this screen, not a verdict on the frameworks.

What was compared

One admin screen: a people list with server-side sort, search and paging, a rows-per-page choice up to 10,000, row selection with a bulk delete behind a confirm dialog, a disable action per row, an add dialog with a validated form (client rules and server field errors), and loading, error and empty states. All three implementations talk to the same mock API process and pass the same Playwright acceptance test, which uses only roles and accessible names and includes an axe-core check (WCAG 2 A and AA): 15 checks, run by npm run accept.

  • xoong 0.0.47: <xo-view>, <xo-table>, <xo-form> and <xo-dialog> from the OpenAPI document, built with xoong build (not minified, not bundled, modulepreload links).
  • React stack: React 19.3.1, TanStack Query 5.107.1, TanStack Table 8.21.3, React Hook Form 7.91.0, zod 3.25.76, built with Vite 8.3.6 (minified, one JS file).
  • Vue stack: Vue 3.5.45, TanStack Query and Table for Vue 5.107.1, vee-validate 4.15.1, zod 3.25.76, built with Vite 8.3.6.

The competitors are written the way their documentation shows, with the libraries most teams reach for, and with the native <dialog> that xoong also uses; none uses a component library, so the stylesheet is a few lines of plain CSS (xoong's comes with the package). All three are served by the same HTTP/2 server (self-signed certificate) with the same brotli compression and the same strict Content-Security-Policy; nothing was tuned per stack. Pages are loaded in a fresh browser context each run, so the cache is cold.

What gets delivered

Sizes are of the files the first view loads, computed from the built files (gzip level 9, brotli level 11), so you can recompute them. xoong's output is not minified: its files are the ones you wrote. A bundler with minification and tree-shaking, applied to the same sources, would make the xoong column smaller; the page compares what xoong build produces today.

Load and interaction, unthrottled

Loopback network, no CPU throttling. "Screen usable" is the first data row drawn and followed by a frame. Interaction times run from the DOM event to the frame after the expected change, so they include the request to the mock API (the same for every stack: sorting is served from a cache there). The search box waits 250 ms after typing in all three, as the xoong search box does; that wait is inside the search time. "Disable one person" is the time until the cell reads "disabled": xoong's entity store updates the row from the server's answer (and, by its default rule, refetches the list in the background afterwards); the two other screens patch their cached pages from the answer and do not refetch.

"JS heap" is the JavaScript heap after a forced garbage collection (CDP Performance.getMetrics). It does not count the memory of the DOM itself, which is why the number of DOM nodes is listed beside it: the stacks differ in both, in opposite directions (xoong: 3.7 MB of JS heap and 37,322 DOM nodes per 1,000 rows; React stack: 15.9 MB of JS heap and 14,010 DOM nodes per 1,000 rows; Vue stack: 10.7 MB of JS heap and 24,012 DOM nodes per 1,000 rows). Neither row is "the memory" of the page. "Total blocking time" is the sum of the time beyond 50 ms of every long task between first paint and "usable"; 0 means no such task, not that no long task ran (script that runs before the first paint does not count).

Unbundled modules: with and without the preload links

xoong build does not bundle: the first view is 35 files. The build writes a <link rel="modulepreload"> for every module of the graph so the browser does not find them one import at a time. The first three columns are the same files: with the links, without them, and over HTTP/1.1 (the worst case for many small files). On the throttled profile the screen is usable after 1,055 ms with the links, 1,270 ms without them and 1,670 ms over HTTP/1.1; unthrottled, on loopback, the three are within 3.1 ms of each other. First paint comes earlier without the links on the throttled profile (392 ms against 720 ms); that was measured, not explained.

Effort: the same screen, written three times

Lines of code are non-blank, non-comment lines of the files a developer writes (markup, script, stylesheet); JSX is counted as script, .vue files are split by block. package.json, lockfiles and the build config are not counted. These are proxies for how much there is to write and read. They are not time: time to a passing screen was not measured, and nobody should infer it from line counts. Two things favour xoong in the table and should be said: its screen assumes an OpenAPI document exists (the other two have a hand-written 25-line API client instead, and would shrink with a code generator), and its look comes from the bundled stylesheet while the other two carry 18 lines of their own. What xoong gives up is control: a table or a form outside what xo-table and xo-form draw is yours to write.

What was not measured

  • How long it takes a person to learn xoong or to build the screen. Not measurable by a script; only lines and dependencies are listed.
  • How well an AI assistant writes xoong on the first try. The scoring harness exists (tools/benchmark/) but no model was run, so there is no score.
  • Real devices, Firefox and Safari, a real network, a long-running page, and screens other than this one (a form-heavy or a rich-text screen may tell a different story).
  • Other frameworks (Angular, Svelte, Solid) and component libraries (MUI, Radix). Adding one means writing the screen and passing the acceptance test.
  • Server-sent live updates: xoong has them built in, the other two screens were not given a live connection, so none was measured.

Run it yourself

cd benchmarks
npm run setup          # npm ci for the competitors and the comparison tools (their own lockfiles; the repository's npm ci is untouched)
npm run accept xoong   # the acceptance test, also: react, vue
npm run bench          # build everything, then runtime.mjs (all tables above except the tools)
npm run cli            # the xoong command, build and dev server
npm run mcp            # the MCP server

The methodology, the environment, the pinned versions and the limitations are in benchmarks/README.md; the raw per-run numbers are in benchmarks/results.
