Benchmarks

Measured, not promised. The same people screen built in xoong, in a React stack, a Vue stack and an Angular stack, run in real Chromium; plus the speed of the xoong command and of xoong-mcp. Every number below is generated from JSON files in the repository by scripts you can run, and the page is rebuilt from that data, so the two cannot drift apart.

Read this first. These are the results of one machine (Apple M1, 8 cores, 8 GB RAM, Darwin 25.2.0 (arm64), Chromium 158.0.8127.18, Node 26.0.0, 2026-11-09) with 5 runs per number after one warm-up run: the median is shown with the smallest and largest run in brackets. Numbers depend on the machine, so use them to compare the columns of one table, not to predict your users' devices. One screen, one team of one author: this is an honest comparison of this screen, not a verdict on the frameworks.

What was compared

One admin screen: a people list with server-side sort, search and paging, a rows-per-page choice up to 10,000, row selection with a bulk delete behind a confirm dialog, a disable action per row, an add dialog with a validated form (client rules and server field errors), and loading, error and empty states. All four implementations talk to the same mock API process and pass the same Playwright acceptance test, which uses only roles and accessible names and includes an axe-core check (WCAG 2 A and AA): 15 checks, run by npm run accept.

  • xoong 0.0.48: <xo-view>, <xo-table>, <xo-form> and <xo-dialog> from the OpenAPI document, built with xoong build (not minified, not bundled, modulepreload links).
  • React stack: written the way a React specialist would write it, with TanStack Table's own sorting, paging and selection state, React Hook Form with zod, TanStack Query, and the native <dialog> without a wrapper. Built with Vite 8.3.6 (minified, one JS file).
  • Vue stack: Vue with TanStack Query and Table, vee-validate and zod, the native <dialog>, built with Vite 8.3.6.
  • Angular stack: Angular 22.2.5, standalone components, signals, resource(), new control flow and reactive forms, with no component or table library (an Angular developer could add Angular Material or the CDK; none was needed for this screen, so none is counted), built with ng build (esbuild). The Angular CLI needs Node 24.15 or newer, so every benchmark of every stack ran on Node 26.0.0.

The rule: a stack is measured with everything it needs for the screen, and each added library counts in full: its bytes in the bundle, its packages in the install count, its install size and time, its lines of code. Nothing is hidden or left out. The libraries of each stack are listed below. The competitors follow their documentation and what an expert of that stack would reach for; none uses a component library, so each carries a short stylesheet of plain CSS (xoong's comes with the package; the other three stylesheets are the same 18 lines). All four are served by the same HTTP/2 server (self-signed certificate) with the same brotli compression and the same strict Content-Security-Policy; nothing was tuned per stack except what that policy needs (next paragraph). Pages are loaded in a fresh browser context each run, so the cache is cold.

How Angular passes the same policy. style-src 'self' and base-uri 'none' forbid things Angular does by default, and each was turned off, not worked around with a looser policy: the build does not inline critical CSS (optimization.styles.inlineCritical: false, which otherwise writes an inline style and an onload handler into the page); all CSS lives in one global stylesheet, because component styles are injected as <style> elements at run time and would need a nonce; and index.html has no <base href> (ng new writes one, and the policy forbids it; this screen has no router). No nonce and no unsafe-inline is used, and no run showed a violation. An application that wants component styles under this policy needs ngCspNonce and a nonce on every response, which a static host cannot give.

Load and interaction, unthrottled

Loopback network, no CPU throttling. "Screen usable" is the first data row drawn and followed by a frame. Interaction times run from the DOM event to the frame after the expected change, so they include the request to the mock API (the same for every stack: sorting is served from a cache there). The search box waits 250 ms after typing in all three, as the xoong search box does; that wait is inside the search time. "Disable one person" is the time until the cell reads "disabled": xoong's entity store updates the row from the server's answer (and, by its default rule, refetches the list in the background afterwards); the two other screens patch their cached pages from the answer and do not refetch.

"JS heap" is the JavaScript heap after a forced garbage collection (CDP Performance.getMetrics). It does not count the memory of the DOM itself, which is why the number of DOM nodes is listed beside it: the stacks differ in both, in opposite directions (xoong: 3.7 MB of JS heap and 37,322 DOM nodes per 1,000 rows; React stack: 10.1 MB of JS heap and 14,016 DOM nodes per 1,000 rows; Vue stack: 10.7 MB of JS heap and 24,018 DOM nodes per 1,000 rows; Angular stack: 1.3 MB of JS heap and 14,017 DOM nodes per 1,000 rows). Neither row is "the memory" of the page. "Total blocking time" is the sum of the time beyond 50 ms of every long task between first paint and "usable"; 0 means no such task, not that no long task ran (script that runs before the first paint does not count).

Unbundled modules: with and without the preload links

xoong build does not bundle: the first view is 35 files. The build writes a <link rel="modulepreload"> for every module of the graph so the browser does not find them one import at a time. The first three columns are the same files: with the links, without them, and over HTTP/1.1 (the worst case for many small files). On the throttled profile the screen is usable after 1,056 ms with the links, 1,255 ms without them and 1,637 ms over HTTP/1.1; unthrottled, on loopback, the three are within 19.5 ms of each other. First paint comes earlier without the links on the throttled profile (392 ms against 724 ms); that was measured, not explained.

Effort: the same screen, written four times

Lines of code are non-blank, non-comment lines of the files a developer writes (markup, script, stylesheet); JSX is counted as script, .vue files are split by block and Angular's component templates are markup. package.json, lockfiles and the build config are not counted. These are proxies for how much there is to write and read. They are not time: time to a passing screen was not measured, and nobody should infer it from line counts. Two things favour xoong in the table and should be said: its screen assumes an OpenAPI document exists (the other three have a hand-written 20-line API client instead, and would shrink with a code generator), and its look comes from the bundled stylesheet while the other three carry 18 lines of their own. What xoong gives up is control: a table or a form outside what xo-table and xo-form draw is yours to write.

What was not measured

  • How long it takes a person to learn xoong or to build the screen. Not measurable by a script; only lines and dependencies are listed.
  • How well an AI assistant writes xoong on the first try. The scoring harness exists (tools/benchmark/) but no model was run, so there is no score.
  • Real devices, Firefox and Safari, a real network, a long-running page, and screens other than this one (a form-heavy or a rich-text screen may tell a different story).
  • Other frameworks (Angular, Svelte, Solid) and component libraries (MUI, Radix). Adding one means writing the screen and passing the acceptance test.
  • Server-sent live updates: xoong has them built in, the other two screens were not given a live connection, so none was measured.

Run it yourself

cd benchmarks
npm run setup          # npm ci for the competitors and the comparison tools (their own lockfiles; the repository's npm ci is untouched)
npm run accept xoong   # the acceptance test, also: react, vue, angular
npm run bench          # build everything, then runtime.mjs (all tables above except the tools)
npm run cli            # the xoong command, build and dev server
npm run mcp            # the MCP server

The methodology, the environment, the pinned versions and the limitations are in benchmarks/README.md; the raw per-run numbers are in benchmarks/results.
