Data flow

A screen reads through one road: the OpenAPI document, a generated table, one client, a query cache, a shared entity store, and the scope of <xo-view>. A write travels back along the same road and refreshes what it touches.

The road from spec to screen

Nothing in the browser knows OpenAPI. xoong sync reads the document once, at development time, and writes a small table that the client uses at run time.

The rest of this page follows the road from the top, then the write path, live updates and errors.

Sync: what the generated files hold

File (in .xoong/)What it is for
operations.jsonThe runtime table. Per operation: id, method, path template, the names of its query parameters, whether it has a body, the request schema (bodySchema, used by forms), and a response descriptor that says where entities sit in the answer. Plus the entities: which schemas are records and which property is their id.
api.d.tsTypeScript types for every operation, so createClient<Operations>() checks names, params and bodies. JavaScript users never load it.
xoong.html-data.jsonCompletion and hover for xo-* names and your operation names in editors. See Tooling.
{
  "version": 1,
  "operations": {
    "listUsers": {
      "id": "listUsers", "method": "GET", "path": "/users",
      "query": ["limit", "sort"],
      "response": { "t": "object", "props": { "items": { "t": "array", "items": { "t": "entity", "name": "User", "replace": true } } } }
    },
    "updateUser": {
      "id": "updateUser", "method": "PATCH", "path": "/users/{id}",
      "body": true,
      "bodySchema": { "t": "object", "props": { "name": { "t": "string", "minLength": 2 }, "email": { "t": "string", "format": "email" } }, "required": ["name"] },
      "response": { "t": "entity", "name": "User", "replace": true }
    }
  },
  "entities": { "User": { "id": "id" } }
}
import { configure } from '@xoong/data';
import '@xoong/data/view';
import operations from '/.xoong/operations.json' with { type: 'json' };

configure({ api: operations, baseUrl: '/api', streamUrl: '/api/events' });
npx xoong sync openapi.json --hints xoong.hints.json

An operation is named by its operationId. Without one, sync builds a name from the method and path. A schema is an entity when it has a property named id, or one named by x-xoong-id in the document, or by a hints file (idNames, or schemas.X.id); an id may be several properties (a composite id). A response that uses the entity's own schema is stored by replacing the record (replace: true above); several schemas that share one entity through a hint merge field by field, because projections carry fewer fields. xoong doctor lists what the document leaves unclear, with a fix for each.

The client

configure() makes the one app-wide client (createClient()); getClient() returns it. Everything that talks to the API goes through it. A request is built like this:

  • The path template is filled from params and every value is URL-encoded; a missing path parameter throws and names it. Only the query names the operation declares are sent; an array repeats the name.
  • headers() is called per request (it may be async: auth tokens). credentials is passed to fetch. The body is JSON, or FormData as it is for multipart operations.
  • Only GET is retried: on a network failure or a 502, 503 or 504, up to retry times (2), waiting retryDelay milliseconds (300) doubled each time. A write is never retried, so it cannot run twice. Fields that hints declare as idempotency keys get a fresh UUID per call.
  • 204 answers null. A hint unwrap: "data" reads { code, message, data } envelopes as data.

A failure is always a XoongError with status (0 for a network failure), title, detail, code, retryAfterS and fields. It is built from application/problem+json, { error: { code, message, fields } }, FastAPI-style { detail: [{ loc, msg }] } or { errors: [{ pointer, detail }] }. A 401 calls onUnauthorized, then every failure calls onError.

The query cache

A read is a query. Its key is the operation id plus the canonical params: keys sorted, empty values dropped, every value as its text in the URL. So the same data is the same query, however you ask for it, and a developer never writes a key.

const a = client.query('listUsers', { limit: 10 });
const b = client.query('GET /users', { limit: '10' });
a === b;   // true: both are the query  listUsers:{"limit":"10"}

A query holds signals: status (idle, loading, success or error), error, the normalised root and data, a computed value that fills the records back in. It also holds the rules of its life:

  • Deduplicated. Two views of the same query share one request.
  • Observed. A view calls retain() when it starts and release() when its params change or it goes away. Retaining fetches the query if it is not fresh (older than staleTime). While a refetch runs, the old data stays on screen and $loading is true.
  • Cancelled. When the last observer lets go while the request is running, the request is aborted. That is not an error; the query returns to its previous state.
  • Collected. A query nobody watches is dropped after gcTime. Coming back before that shows the cached data at once.

The entity store

When a response arrives, the response descriptor tells normalize() where the records are. Each record goes into the store once, under Name#id, and the query keeps a reference ({ $ref: "User#1" }) in its place. Every record is one signal. A GET response is only one of four ways a record gets in:

const q = client.query('listUsers', { limit: 10 });
await q.fetch();
q.root.peek();                 // { items: [{ $ref: 'User#1' }, { $ref: 'User#2' }], total: 2 }
client.store.read('User#1');   // { id: 1, name: 'Ada', email: '...' }  (a tracked read)
q.data.peek();                 // the same list with the records filled in

The effect is sharing: a list, a detail page and a dashboard that show User#1 read the same signal, so one change reaches all of them. Reading the data (denormalize) resolves the references; a reference to a deleted record drops out of lists instead of leaving a hole. A union is stored under the right entity when the members can be told apart (a discriminator, a fixed tag value, or a property only one member has); otherwise the value stays inline and xoong doctor reports it (XO160).

derived(({ all, get }) => ...) is a computed over the store: all("Order") is every loaded order, from any query, and the result recomputes when one of them or the set changes. It never fetches; fetching is declared on a view.

One caveat. When a query is collected, records that no remaining cached query reaches (following nested references) are dropped, and a screen still reading them sees them as deleted. So a screen should show its data through a query. Turn it off with evictEntities: false.

The view and the DOM

<xo-view get> picks its query in an effect over its get attribute and its params (the p-* attributes, xo-param, the URL). When either changes, it releases the old query and retains the new one. Its scope has $loading (status is loading), $error (the XoongError), the response fields (items), and the params, so {id} works in an action. Text bindings read the scope inside effects, so only the nodes whose values changed are written. Rendering shows how.

<xo-view get="listUsers" p-limit="10">
  <p xo-if="$loading" aria-busy="true">Loading…</p>
  <p xo-if="$error" role="alert">{$error.code}: {$error.detail}</p>
  <ul>
    <li xo-each="items">
      {name}
      <button xo-click="POST /users/{id}/disable" xo-optimistic="status=disabled">Disable</button>
    </li>
  </ul>
</xo-view>

The write path

A write is xo-click on a button or xo-submit on a form. Both end in client.mutate(op, params, body).

  1. The handler. It ignores a second click while one call is running (and sets aria-busy). xo-confirm asks first. Path and query params come from the scope: the current item first, then the view's p-* params. The body is the form model's result, the form's fields, xo-body (a record from the scope), plus xo-with fields; xo-selected runs once per ticked row or sends the ticked ids in one request.
  2. Optimistic update. With xo-optimistic="status=disabled" (or the optimistic option), the patch is applied to loaded records at once. If the call fails, only the fields that still hold the provisional value are put back, so a newer change from the server or another screen is never erased.
  3. The response is normalised into the store, so every screen that shows the record updates. The call resolves with the denormalised result.
  4. Invalidation. Every cached query whose path overlaps the mutation's path is marked stale, and refetched now if something is watching it. Two paths overlap when one is a prefix of the other, segment by segment.
  5. Events. The view's host fires xo-done with the result, and xo-notice when the button has a xo-notice message (shown by <xo-toast>).
Cached queryAfter POST /users/1/disable
GET /usersrefreshed (a prefix of the mutation's path)
GET /users/1refreshed, unless the response was that very record: it was just rewritten, so it is marked fresh instead
GET /users/1/postskept (neither path is a prefix of the other)
GET /users/2kept (differs at a segment)

The rule is by path, so it needs no declaration. When it is not enough, name the extra queries once: configure({ invalidate: { shipOrder: ["getDashboard"] } }). Those are refreshed whatever their path.

await client.mutate('updateUser', { id: 1 }, { name: 'Ada L.' }, {
  optimistic: [{ $ref: 'User#1', patch: { name: 'Ada L.' } }],
});

A deleted record is not removed from the store by a DELETE call: the lists that contained it refetch and no longer name it. Only a stream delete event removes a record at once.

Server-known data: seed

When the server already has the answer (it rendered the page), put it in the cache instead of asking again. The server writes the JSON into the page as <script type="application/json"> (not code, so a strict CSP allows it), one module script calls client.seed(op, params, data), and the data is stored like any response, entities included. A view that asks for the same operation and params shows it at once and makes no request until it is stale.

// main.js: the server wrote the answer into the page as <script type="application/json" id="seed-users">
const data = JSON.parse(document.getElementById('seed-users').textContent);
getClient().seed('listUsers', { limit: 10 }, data);
// a view with get="listUsers" p-limit="10" shows it at once and makes no request until it is stale

Live updates

With streamUrl set and live on a view, the client opens one server-sent events connection, shared by all live views and closed when the last one goes away. It is loaded lazily, so an app without live views never pays for it. Each message is one JSON event, applied to the store, not to a view: every screen showing that record updates.

{ "type": "patch",  "entity": "User", "id": "42", "path": "/email", "value": "a@b.c", "version": 17 }
{ "type": "upsert", "entity": "User", "id": "42", "value": { "id": 42, "name": "Ada" }, "version": 18 }
{ "type": "delete", "entity": "User", "id": "42", "version": 19 }
{ "type": "resync" }
  • patch changes one field, addressed by a JSON Pointer (/email); it is ignored if the record is not loaded. upsert merges fields into the record, or creates it. delete removes it.
  • version must rise per record. An event with a version at or below the last applied one is dropped, and a delete keeps its version so a late event cannot bring the record back.
  • resync forgets the versions and marks every cached query stale. So does a reconnect after an interruption: events may have been missed, so what is on screen is refetched. Replay by Last-Event-ID is the browser's EventSource doing its job; the client adds no replay of its own.

When something fails

  • A read fails (after the retries): the query's status is error, $error holds the XoongError, any earlier data stays, and onError runs. xo-refresh on a button fetches again.
  • A write fails: the optimistic patch is undone, onError runs, and the view's host fires xo-error with the error. <xo-toast> listens for it. In a form, error.fields are put on the fields they name (see Forms flow).
  • A screen mistake (an unknown operation name in get) is not an API failure: it is logged with console.error together with the closest valid name, xo-error fires, and the rest of the screen keeps working.

Where to look in the code

  • packages/cli/src/openapi.js: the analysis behind sync: entities, response descriptors, request schemas
  • packages/data/src/client.js: request building, retries, XoongError, queries, mutate, seed, stream
  • packages/data/src/invalidate.js: the path-overlap rule
  • packages/data/src/store.js: normalisation, the entity signals, stream events, optimistic updates, eviction
  • packages/data/src/stream.js, default.js: the SSE connection and its sharing
  • packages/data/src/view.js: <xo-view>, scope variables, the action handlers
  • docs/data-layer.md: the longer design notes (parts of it, such as per-view stale and the gateway, are not built)
