# Testing

Status: **Draft** (prototype in `packages/test`). Runner: **Vitest**.

UI is hard to test in most frameworks because the thing under test is hidden:
a virtual DOM, Shadow DOM boundaries, hydration, framework internals and
hand-written HTTP clients that each need their own mock. xoong removes those
obstacles by design, so a screen test is a test of real DOM against a fake network.

## Why xoong screens are easy to test

| Obstacle elsewhere | In xoong |
|---|---|
| Shadow DOM hides elements from queries | Light DOM only: `querySelector` sees everything |
| Virtual DOM / renderer-specific test utils | Real DOM, no special renderer |
| Hydration and server/client differences | None: server HTML is the DOM |
| Mocking many `axios`/`fetch` clients | One seam: the network. `mockApi` is built from `operations.json` |
| Flaky timing (`await` roulette) | `settle()` waits until no request is in flight |
| Live/real-time features are untestable | `screen.push(event)` delivers a stream event |
| Hidden state in hooks | State lives in signals and the entity store, observable from the DOM |

## Three layers

1. **Unit** (no DOM): pure functions, `derived`, the store. Plain Vitest.
2. **Screen** (happy-dom, fast): `mount` + `mockApi`. Covers rendering, actions,
   errors, live updates.
3. **End to end** (real browser): Playwright, or Vitest browser mode. Selectors
   are stable because they are tags, attributes and `data-*`, not generated names.

## Writing a screen test

```js
import { describe, it, expect, afterEach } from 'vitest'
import { mount, mockApi, respond } from '@xoong/test'
import table from '../.xoong/operations.json'   // generated by `xoong sync`

let screen
afterEach(() => screen?.unmount())

it('disables a user', async () => {
  let name = 'Ada'
  const api = mockApi(table, {
    listUsers:   () => [{ id: 1, name }],
    disableUser: () => { name = 'Ada (off)'; return { id: 1, name } },
  })
  screen = await mount(`
    <xo-view get="/users">
      <li xo-each="."><b>{name}</b>
        <button xo-click="POST /users/{id}/disable">off</button></li>
    </xo-view>`, { api })

  await screen.click('button')
  expect(api.callsOf('disableUser')[0].params).toEqual({ id: '1' })
  expect(screen.text('b')).toBe('Ada (off)')
  expect(api.unhandled).toEqual([])      // nothing unexpected was called
  expect(screen.errors).toEqual([])
})
```

### API

| Helper | Purpose |
|---|---|
| `mockApi(table, handlers)` | fetch replacement keyed by `operationId` or `"METHOD /path"`. Records `calls`, lists `unhandled`. Handlers return data or `respond(status, body)` |
| `mount(html, { api })` | Renders HTML with the real data layer against the mock; returns a screen |
| `screen.$ / $$ / text / texts` | Query helpers |
| `screen.click(target)` / `submit(form, fields)` | Interact, then wait until idle |
| `screen.push(event)` | Deliver a stream event (`patch`/`upsert`/`delete`) |
| `screen.settle()` | Wait until requests and updates settle |
| `screen.errors` | `xo-error` events seen (API failures and screen mistakes) |
| `screen.unmount()` | Cleanup |

## Running

```bash
npm test                  # everything (Vitest)
npm run test:watch        # watch mode
npm run test:logic        # pure logic + real-browser tests (Node environment)
npm run test:screens      # screen tests in happy-dom
npm run test:coverage     # everything, with coverage thresholds enforced
```

Config lives in `vitest.config.mjs`: two projects. `logic` runs in Node (the real-browser tests
drive Chromium through Playwright); `screens` runs in happy-dom. TypeScript spec files work
without extra setup because Vitest transpiles them. Browser tests use the Chromium named by
`XOONG_CHROMIUM` when set, otherwise Playwright's own (`npx playwright install chromium`).

## How xoong tests itself

| Layer | What it checks |
|---|---|
| Unit | Signals, store, normalization, client (cache, invalidation, retry, errors, streams), CLI and OpenAPI analysis |
| Real browser | Templates, `XoElement`, `<xo-view>` against a fake backend over HTTP and SSE |
| happy-dom mirror | The same template and element behaviours, so coverage can measure them and the two environments cross-check each other |
| Screen (`@xoong/test`) | `mount` + `mockApi` flows, including a chat client built on a real (anonymised) API spec |
| Architecture (`test/architecture.test.mjs`) | Zero runtime dependencies, import direction, no Node built-ins or DOM at import time in pure-logic modules, gzip size budget, MIT licensing |
| End to end (`examples/admin/test/e2e.test.mjs`) | Mock backend, `xoong dev`, two real Chromium tabs: list, click, live update across tabs, resync, error envelope, delete, TypeScript stripping |
| Corpus (`tools/corpus.mjs`) | Real-world OpenAPI documents: analysis, generated types compile, YAML equals JSON. See [test-corpus.md](test-corpus.md) |

Coverage gates (statements 88 / branches 79 / functions 88 / lines 92 overall, stricter for `core`)
are set just under the measured values, so a drop fails the build. CI (`.github/workflows/ci.yml`)
runs the suite with coverage on Node 22 and 24. Screen tests for `@xoong/ui` live in `packages/ui/test`; the admin example is covered end to end in `examples/admin/test`.

The development toolchain needs Node 22.12 or newer: Vitest 5 declares that range, and on Node 20 its
reporter crashes (`Map.groupBy is not a function`) while one data test uses `Object.groupBy`. The first
CI run failed this way on Node 20, so Node 20 was dropped from the matrix. Whether the runtime packages
(`cli`, `server`) work on Node 20 is not verified; the browser packages do not run on Node at all.

## Rules of thumb

* Mock the network, never the data layer. The cache, store and invalidation are
  part of what you are testing.
* Assert `api.unhandled` is empty so an unexpected request fails the test.
* Use `xo-*` attributes and element names as selectors; avoid positional ones.
* Use real-browser tests for what happy-dom cannot emulate (layout, focus
  behaviour, native `<dialog>` and Popover details).
