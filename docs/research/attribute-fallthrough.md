# How other libraries keep attributes the author wrote

Notes for [ADR-0014](../decisions/0014-attributes-survive-templates.md). Read in November 2026 from the current guides: [Vue](https://vuejs.org/guide/components/attrs), [Ember](https://guides.emberjs.com/release/components/component-arguments-and-html-attributes/), [Angular host elements](https://angular.dev/guide/components/host-elements), [Lit properties](https://lit.dev/docs/components/properties/), [Stencil properties](https://stenciljs.com/docs/properties), [Svelte `$props`](https://svelte.dev/docs/svelte/v5-migration-guide) and [`class`](https://svelte.dev/docs/svelte/class), [Alpine `x-bind`](https://alpinejs.dev/directives/bind), [htmx inheritance](https://htmx.org/docs/#inheritance) and the swap/settle description on the same page.

xoong's template elements (`<xo-table>`, `<xo-pager>`, `<xo-form>`, and anything registered with `defineTemplate`) are removed and replaced by ordinary markup. The author's attributes have to be moved, or they vanish with the host. That is the same problem Vue, Ember and Svelte have. It is not the problem Angular, Lit, Stencil, Alpine or htmx have, because those leave the element the author wrote in the document.

## What each one does

| Library | Does the host stay? | Attributes the component did not declare | `class` and `style` | Where it is decided | When it is applied |
| --- | --- | --- | --- | --- | --- |
| Vue 3 | No. The component renders its own root | Fall through onto that root automatically. A declared prop or emit is not in `$attrs`. `inheritAttrs: false` turns the automatic step off; the component then places `v-bind="$attrs"` itself. A component with more than one root does not receive them automatically (Vue warns); the author binds `$attrs` | Merged with the root's own `class` and `style`. The fallthrough value wins a conflicting style property | The renderer, from what was not declared | During render, on the vnode, before the DOM commit |
| Ember | No. The template says where they go | Not automatic. `...attributes` on an element in the component template is the only place they land. `@arguments` are not HTML attributes and are not in `...attributes` | `class` is merged (the component's classes, then the caller's, when `...attributes` comes after `class`). Every other attribute follows source order: `...attributes` after an attribute overrides it; `...attributes` before an attribute does not | The component author, by where they write `...attributes` | During render |
| Svelte 5 | No | Not automatic. `let { known, ...rest } = $props()` removes the declared props; `{...rest}` on an element forwards the rest. Svelte 3/4 used `$$restProps` the same way. Forgetting the spread drops the attributes | Not merged by the spread. A later `class` or `{...rest}` replaces the earlier one. The documented pattern pulls `class` out and combines it (`class={['cool-button', props.class]}`) | The component author, by the spread | Compiled into the DOM update |
| Angular | Yes. The selector element is the host; the template is rendered inside it | Stay on the host. Nothing is copied onto an inner element. `host: { ... }` and `@HostBinding` write the component's own attributes onto that same host. `HostAttributeToken` reads a static attribute; it does not remove it | On a collision, template bindings beat static template values, which beat directive host bindings, which beat component host bindings, which beat static host values. A static attribute written at the use site beats a static host value | The host element itself | Change detection, on the host |
| Lit | Yes. The custom element is the component | Stay on the host. A `@property` observes an attribute (and, with `reflect: true`, writes the property back). `attribute: false` or `@state` does not touch an attribute. An attribute with no property is left alone | No merge step. The host's `class` and `style` are the ones the author wrote, unless the component's render writes them | `attributeChangedCallback` for declared properties only | On the host, before and during update |
| Stencil | Yes, same as Lit | Stay on the host. `@Prop()` listens for the matching attribute (`isComplete` is `is-complete` unless `attribute` renames it). `reflect: true` writes the value back. An undeclared attribute is not observed and not removed | No merge step. The `Host` render can set host attributes; undeclared ones remain | The compiler's attribute-to-prop map | On the host |
| Alpine | Yes. `x-data` enhances the element that carries it | Stay, because nothing replaces the element. `x-bind` / `:` sets one attribute from an expression. `x-bind="obj"` can apply a bag of attributes to an element the author names | `x-bind:class` adds and removes tokens and keeps classes already on the element (the object form does not wipe the attribute). `x-bind:style` as an object is appended to the existing `style` | The directive, on that element | When Alpine starts, then on each change. `[x-cloak] { display: none }` hides raw markup until then |
| htmx | Yes, until a swap replaces it | Stay. htmx does not re-parent attributes onto a component root. `hx-*` attributes are inherited by descendants (so one `hx-confirm` covers a group); `hx-disinherit` and `hx-confirm="unset"` opt out. That is inheritance down the tree, not fallthrough onto a replacement | No merge. On a swap, htmx finds the previous element with the same `id`, copies its attributes onto the new element, swaps, then after the settle delay (20ms) writes the new attributes. The copy exists so a CSS transition can see the old value. `hx-preserve` keeps a node itself instead of merging attributes | The server sends the new attributes; settle is the only client copy | Two steps on purpose, a frame apart, and only for an `id` match |

## What is worth copying

* **Declared versus left over.** Vue props, Ember `@arguments`, and Svelte's destructured props are consumed by the component. Everything else belongs to the author. A template in xoong should have the same split: `take(name)` reads an attribute the component handles and removes it; whatever is still on the host afterwards is the author's.
* **One automatic target, not a second syntax.** Vue puts a single root's fallthrough on by default, and makes the author aim `$attrs` only when the root is the wrong element or there are several. Ember and Svelte always make the author aim. xoong's built-in templates each have one element root (`div.xo-table`, `nav.xo-pager`, `form.xo-form`), and a third-party template that returns a fragment is the odd case. Automatic placement on the first element root matches the common case. A fragment does not get Vue's dev-mode warning (that string would be paid on every page); the rule is written down instead, and attributes the author needs on a later sibling are written on that sibling in the template.
* **`class` is appended, `style` is chained, anything else is replaced.** Vue and Ember both merge classes so the component's hooks (`.xo-table`) survive. Ember puts the caller's classes after the component's. Vue and Alpine let the caller's style win a property conflict by applying it after the component's. Ember's source order and Angular's "the use site beats a static host value" agree that for a normal attribute the author wins. `style="component; author"` is the same rule for declarations inside one attribute.
* **Apply it before the node is in the document.** Vue, Ember and Svelte set the attributes on the way into the DOM. htmx's settle copy is the counter-example: it changes attributes on a live element a frame later, on purpose, for a transition. Doing that for template expansion would paint the component's attributes and then the author's. The copy belongs on the detached node, and the fragment's children have to be remembered before `replaceWith`, which moves them and leaves the fragment empty.
* **Do not invent a cloak attribute.** Alpine removes `x-cloak` when it starts; xoong already hides an undefined `<xo-view>` that is not a prerender (`xoong.css`). The host elements are not custom elements (nothing calls `define('xo-table')`), so `:not(:defined)` is true for their whole life. Hiding those tags until they are replaced covers a host that sits outside `<xo-view>` and is therefore never expanded. A `<template>` is already inert: its contents are not shown, inside or outside a view.

## What we are not taking

* Ember's and Svelte's explicit spread as the only mechanism. Every built-in template would have to remember it, and a forgotten spread is a silent drop. The owner rule is that the shared layer does this, not each component.
* Keeping the host, as Angular, Lit and Stencil do. The rendered table would be wrapped in `<xo-table>`, which is the opposite of the light-DOM markup those templates produce today.
* htmx's two-step settle. There is no transition to preserve, and the second write is a frame of the wrong attributes.
* Reflecting a property back onto an attribute the author set (Lit and Stencil `reflect`). Reflection overwrites the author. The only attribute a component removes or rewrites is one it took, or one it set itself (an `aria-label` it owns).
